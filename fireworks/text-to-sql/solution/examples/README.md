# Example schema library

Eight ready-to-use schemas so a user can ask this system questions
immediately, without first authoring or uploading their own schema.

## Attribution

The schemas themselves -- table names, columns, and relationships -- are
vendored, byte-for-byte, from
[**codeunion/examples-schema**](https://github.com/codeunion/examples-schema),
© 2014 CodeUnion, Inc., **MIT licensed**. See [`LICENSE`](LICENSE) for the
full text (also reproduced verbatim from upstream). Nothing in
`examples/schemas/*/*.postgres.sql` has been edited -- diff any of them
against upstream and they match exactly.

Everything else in this directory (`graph.json`, `sqlite.sql`, `seed.sql`,
`NOTES.md`, and the seed data itself) is generated by this repository's own
code (`examples/generate_examples.py`) and is **not** part of the upstream
project -- upstream ships schema DDL only, no seed data.

## Why this exists, mechanically (D6 in action)

`memory/decisions.md` D6 says a `DataModelVersion` stores a dialect-neutral
JSON entity graph, and a `Schema` is that graph rendered to concrete DDL for
one engine -- "purist model, pragmatic projection," not just a claim. This
library is that claim, exercised for real:

```
<name>.postgres.sql  --foundation.ddl.parse_ddl-->  graph.json  --foundation.ddl.render_ddl-->  sqlite.sql
     (vendored,                (EntityGraph,                        (D5: the only dialect
      Postgres dialect)         dialect-neutral)                      this codebase executes)
```

Upstream leans on Postgres's `ALTER TABLE ... ADD UNIQUE` / `ADD FOREIGN KEY`
for constraints added after the fact -- including a genuinely **circular**
foreign-key pair in `question_answer` (`questions.best_answer_id` references
`answers.id`; `answers.question_id` references `questions.id`; each is added
via a separate `ALTER TABLE` because neither table can forward-reference the
other inline), and, in `tic_tac_toe`, a **literal duplicate** constraint
(`ALTER TABLE turns ADD UNIQUE (game_id, position);` appears twice). SQLite
cannot express any of `ALTER TABLE ... ADD UNIQUE`, an unnamed `CREATE INDEX`,
or a duplicate index -- so a naive "run the Postgres DDL through SQLite"
approach fails on exactly these files.

`foundation.ddl.parse_ddl` folds `ALTER TABLE ... ADD UNIQUE` / `ADD FOREIGN
KEY` into the *same* graph table as if the constraint had been declared
inline, in a second pass after every `CREATE TABLE` is parsed -- so
declaration order and circularity stop mattering, and a structurally
duplicate constraint is silently deduped rather than appended twice. See
`packages/foundation/src/foundation/ddl.py`'s module docstring ("ALTER-expressed
constraints") for the exact mechanism. The result: all 8 schemas render to
valid, executable SQLite DDL -- the graph never cared that the constraint
arrived via `ALTER` instead of `CREATE`.

`CREATE INDEX` statements (named or not) are intentionally **not** captured
in the graph -- `foundation.graph`'s docstring lists indexes as deliberately
out of scope for the dialect-neutral model (a workload/dialect concern, not a
schema-shape one). They show up as `parse_ddl` warnings, not errors.

## What did not survive ingestion, and why

- **Postgres `SERIAL` / `SMALLSERIAL` / `BIGSERIAL`** are not real data types
  (they're sugar for "integer column + sequence + `DEFAULT nextval(...)`")
  and are not in sqlglot's canonical type vocabulary the graph validates
  against. Every `id SERIAL PRIMARY KEY` in these schemas is captured as a
  plain `INT` primary key; the sequence/autoincrement behavior itself is
  dropped. In practice this doesn't matter for a solo, unnamed primary key:
  `render_ddl` already renders it as SQLite's `INTEGER PRIMARY KEY`, which
  SQLite treats as a `rowid` alias and auto-assigns on insert.
- **`tic_tac_toe`'s `turns` table carries a real oddity, not a bug in this
  pipeline.** Beyond the duplicated `UNIQUE (game_id, position)` mentioned
  above, the source *also* contains `ALTER TABLE turns ADD UNIQUE (game_id);`
  -- a distinct, separately-declared constraint that limits the table to **at
  most one row per game**. That contradicts the file's own leftover comment
  ("every turn ... would result in a new entry in the `turns` table") and
  looks like an upstream authoring slip. This pipeline ingests it faithfully
  rather than silently dropping a constraint that parses and executes without
  error -- so the seed data for `tic_tac_toe` records at most one turn per
  game (most games; a fifth have none, the "zero children" case). See
  `examples/schemas/tic_tac_toe/NOTES.md`.
- Every other construct in all 8 files round-trips into the graph; see each
  schema's `NOTES.md` for its exact `parse_ddl` warning list (mostly just the
  `SERIAL` note above, plus one warning per skipped `CREATE INDEX`).

All 8 schemas load, render, and seed into real SQLite -- none were dropped.

## Layout

```
examples/
  LICENSE                       # upstream's MIT license, verbatim
  README.md                     # this file
  generate_examples.py          # regenerates everything below (deterministic, fixed seed)
  schemas/<name>/
    <name>.postgres.sql         # vendored upstream DDL, byte-identical to upstream
    graph.json                  # EntityGraph produced by parse_ddl (committed)
    sqlite.sql                  # render_ddl(graph, "sqlite") (committed)
    seed.sql                    # deterministic seed INSERTs, generated (not from upstream)
    NOTES.md                    # parse_ddl warnings + row counts for this schema
```

## Seed data

Upstream ships schema only, no data. `generate_examples.py` generates
deterministic seed rows (fixed RNG seed derived from the schema name, no
external source) for every table, sized to a modest 20-100 rows per table and
built to be referentially valid *and* to contain the edge cases that make
questions interesting to ask against these schemas:

- **NULLs in nullable columns**: `question_answer.questions.best_answer_id`
  (half of answered questions leave it unset), `tic_tac_toe.games.winner_id`
  and `hangman.games.completed_at` (in-progress/drawn games), and every
  top-level `reddit.comments.parent_id`.
- **An entity with zero children**: an unanswered question, a tag-less
  article, a comment-less submission, a photo-less album, a response-less
  survey, a turn-less hangman game, and (structurally, from the constraint
  above) most `tic_tac_toe` games.
- **A tie at a boundary**: `blog_with_likes` articles 1 and 2 are seeded to
  the same like count (the top of a "most-liked article" ranking is
  genuinely ambiguous); `reddit` submissions 1 and 2 are similarly tied at
  the top of the score ranking; `tic_tac_toe` includes drawn games
  (`winner_id IS NULL` with `completed_at` set).

Regenerate with:

```
uv run --project packages/foundation python examples/generate_examples.py
```

This is idempotent and deterministic -- re-running it reproduces the exact
same committed bytes (the script also self-checks every schema by loading
its rendered DDL and seed into a real in-memory SQLite database before
writing anything to disk).

## Using the library from code

```python
from foundation.examples import list_examples, load_example

for info in list_examples():
    print(info.name, info.table_count, info.description)

graph, sqlite_ddl, seed_sql = load_example("question_answer")
# sqlite_ddl -> foundation.sample_db.create(...)
# seed_sql   -> executescript against the resulting database
```
